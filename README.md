# Petek Staff Scheduler

A browser-based tool that automatically builds the weekly staff schedule for a bookstore, stationery shop and café with about a dozen employees. It replaces a schedule that managers used to build by hand every week, and it is now in daily use by the shop.

The interface is in Turkish, since it was built for a real shop in Türkiye.

## Try it

**[Open the demo](https://hasanakkaya0.github.io/petek-scheduler/app/?deneme)** (`?deneme` = demo mode)

1. Click **"Örnek personeli yükle"** (Load sample staff) in the orange bar at the top.
2. The app loads a made-up team of 12 and generates this week's schedule in one click.
3. Click any cell to edit it, drag a shift onto another cell to copy it, or press **"Haftayı otomatik oluştur"** to regenerate.

Demo mode keeps everything in your own browser, in a separate store, and never touches the real shop's data. The real installation at `/app/` (without `?deneme`) requires a login.

## The problem

Every week a manager had to decide who works which day, who opens, who closes and who is off, while keeping several rules in mind at the same time:

- Each section (cashier, stationery, textbooks, photocopy, café) needs a minimum number of people at every hour.
- Everyone has a daily hour quota (9 or 10 hours, less for part-time staff).
- Everyone gets one day off per week, and nobody gets both weekend days off.
- Some sections can only be covered by specific people. The café block is critical and must never be left empty.

Doing this by hand was slow and error-prone. The tool generates a full week in one click, checks it against every rule and reports any gap it could not close, so a person can fix it.

## How it works

The core is `generateWeek()` in `app/js/generator.js`. It builds the week step by step:

1. **Protect manual decisions.** Annual leave, manually entered days off and locked shifts are never changed.
2. **Pick days off.** A scoring function picks each person's day off based on their preference, balance across the week and rest between shifts. Hard rules come first: a day is not allowed if it would leave a critical section without anyone qualified.
3. **Assign shifts.** Opening and closing shifts are distributed within each section, with a weekly cap on closings per person.
4. **Fill gaps.** If a section is short at some hour, a qualified person is borrowed from a section that has extra staff, using a time-based task block inside their shift.
5. **Assign the evening supervisor.** Rotates among eligible people who stay until closing.
6. **Balance closings.** A final pass swaps shifts so closings are spread fairly, without breaking coverage.
7. **Report.** Remaining gaps are split into "not enough staff" and "needs a manual decision".

Design choices:

- **Rule-based greedy generator instead of a full optimizer.** The shop's rules kept changing, so every decision had to be explainable ("why is this person off on Friday?") and new rules had to be easy to add. The trade-off is that the result is not guaranteed to be optimal, which is why there is a balancing pass and a gap report.
- **Hard vs. soft constraints.** Coverage of critical sections is never violated. Personal preferences only affect the score.
- **No automatic overtime.** Overtime happens in real life, but a person writes it, not the system.

## Features

- Staff, sections, coverage rules and opening hours are all editable from the interface, no code needed
- **Opening hours are dated:** a new schedule of hours (for example "closing at 20:00 from November") applies from a given date and leaves past weeks and balances untouched
- Manual editing with locked cells, drag and drop, and multi-step undo
- Week lock, so a schedule already shared with staff is not regenerated by mistake
- Annual leave tracker and a weekly hours balance
- Live status panel that flags rule conflicts on every change
- **Cloud sync between computers**, with an offline cache and a warning when two people have the same week open
- Three tabs (Schedule / Counters / Settings), a refresh button that always fetches the newest version
- Export the week as a PNG image and back up all data as JSON
- Works on phones and tablets

## Architecture: data and sync

The app is plain HTML, CSS and JavaScript with no framework and no build step. It runs from static hosting (GitHub Pages) and keeps its data in Firebase.

```
browser  ──  Firebase Auth (shared login)  ──  Firestore (europe-west1)
   │                                              workspaces/petek/kv/<key>
   └── in-memory cache  ◄── live snapshot listener ◄── other computers
```

- **One document per week.** The settings (staff, rules, balances) and each week are separate Firestore documents (`settings`, `week:2026-10-19`, …), so two people editing different weeks never overwrite each other.
- **Everything is loaded into memory at start-up.** The reports that scan all weeks (hours balance, annual leave) read from memory and never wait for the network.
- **Offline first.** Firestore's local cache lets the app work without a connection and sends the changes when it is back.
- **Live updates.** A change made on another computer arrives through the snapshot listener and the screen refreshes. If two computers have the same week open, a banner warns that the last save wins. Presence is a small `presence:<id>` record refreshed every 30 seconds.
- **Safe by default.** An empty week is not written to the cloud until it is first edited, so a computer that has not received the data yet cannot overwrite a filled week.
- **Storage is behind one interface** (`store.get / set / listKeys`). The same code runs on Firestore, on `localStorage` (demo mode, local files) or in tests with a fake server.

### Security and privacy

- The data is protected by Firestore security rules on the server, not by the client code. Only the shop's account (by user id) can read or write, and everything else is denied.
- The Firebase web configuration in `app/js/firebase-config.js` is public by design. It identifies the project; the rules and the login protect the data.
- **No real data is in this repository.** Staff names, schedules, backups and the access rules are kept out of it, and names that appear in code comments are anonymised before publishing.

## Project structure

```
app/
  index.html            main page, data model, start-up
  css/styles.css
  js/generator.js       scheduling engine (generateWeek, computeOffDays)
  js/validation.js      rule checks and live status panel
  js/render.js          schedule grid, drag and drop, undo
  js/settings-panels.js staff, section and rule settings
  js/shop-hours.js      dated opening hours
  js/ledger.js          weekly hours balance
  js/yillik-izin.js     annual leave tracker
  js/bulut.js           cloud storage (Firestore), login screen, live updates
  js/birlikte.js        "same week open elsewhere" warning
  js/storage.js         storage interface, demo mode, status badge
  js/sekmeler.js        tabs
  js/ornek-veri.js      made-up sample staff for demo mode
  js/export-png.js      PNG export
  js/modals.js, utils.js, firebase-config.js
index.html              redirects to app/ (GitHub Pages)
paketle.js              bundles everything into a single HTML file
surumle.js              stamps css/js URLs with a version (see below)
testler/                automated tests (Node.js)
```

**Cache busting.** GitHub Pages caches files for ten minutes, which can show a new page with an old stylesheet. `surumle.js` appends `?v=<timestamp>` to every local script and stylesheet URL before each release, so a browser can never mix versions.

## Running it

- **Online:** open the hosted `app/` page (login required), or add `?deneme` for the demo.
- **Locally:** open `app/index.html` in a browser. Opened as a file, it keeps data in that browser only and does not use the cloud.
- **Single file:** `node paketle.js` creates `dagitim/PetekProgram.html`, which can be copied to another computer.

## Tests

`node testler/calistir.js` runs about 200 automated checks in Node.js without a browser or a network connection.

- A rule audit generates several weeks and scans each one for violations: missing days off, quota or weekly hour overruns, coverage below the minimum, missing or early-leaving supervisor, closing cap overruns, unqualified assignments and shifts outside opening hours.
- Tests for specific bugs that were found and fixed (days off, week lock, annual leave, drag and drop, staff removal, closing caps).
- **The cloud layer is tested against a fake Firestore server**: opening, writing, echo suppression, changes from another computer, permission errors, time-outs, and the "do not overwrite with an empty week" rule.
- Tests for dated opening hours, tabs, the same-week warning, the refresh button and the sample data (the generated week must have no one working seven days, no quota overruns and at most three open gaps).

The rule audit and some bug tests use a backup of real schedule data, which is not included in this repository for privacy reasons; the sample staff in demo mode is the public stand-in.
